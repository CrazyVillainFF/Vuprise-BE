# Production feature configuration

The web client is deployed on Vercel, while the API is an Express service described by `render.yaml`. Server-only credentials must be configured on the API service, not in `VITE_*` variables.

## Password recovery (Brevo email OTP)

- The user enters their email, receives a six-digit code, then submits that code with a new password. The code is cryptographically generated, stored only as a peppered HMAC digest, expires in 10 minutes, allows at most five wrong attempts, and is invalidated when used.
- Requests for known and unknown accounts return the same generic confirmation. Brevo delivery rejection is reported as an error instead; the temporary code is invalidated and the backend does not pretend that delivery succeeded.
- Set `BREVO_API_KEY` in the Render API service environment. The server sends through Brevo's transactional HTTP endpoint (`POST https://api.brevo.com/v3/smtp/email`) using the `api-key` header; SMTP is not used. Keep the API key secret and do not add it to Vercel client variables.
- Set `PASSWORD_RESET_PEPPER` to a long, random server-only secret. The Render blueprint generates one when it creates the service. Do not change it after codes are issued; it is used to verify the stored digests.
- `BREVO_SENDER_EMAIL` is the verified Brevo sender address and defaults to `vupriseofficial@gmail.com`; `BREVO_SENDER_NAME` is its display name and defaults to `Vuprise`. `PASSWORD_RESET_FROM` is still honored as the sender-email fallback for deployments that define it. Configure these on the Render backend only, never in a `VITE_*` variable. Brevo must show this sender as verified and allow transactional email sending for the account.
- `CLIENT_URL` remains the deployed frontend origin (`https://nexora-lac-three.vercel.app`) for the application, but the OTP flow does not place a reset token or link in email.
- If Brevo rejects the sender, recipient, or request, the API returns an error and invalidates the temporary code. Backend logs contain only a safe error category, not the recipient, OTP, API key, request headers, or provider response body.
- A successful Brevo API response means the provider accepted the send request, not that the message reached the recipient's inbox. Verify actual delivery to an intended recipient before treating end-to-end delivery as confirmed.
- On Render, configure `BREVO_API_KEY`, `BREVO_SENDER_EMAIL=vupriseofficial@gmail.com`, `BREVO_SENDER_NAME=Vuprise`, and `PASSWORD_RESET_PEPPER`; retain the existing `CLIENT_URL=https://nexora-lac-three.vercel.app` application setting. Redeploy the backend after changing environment values. The client only needs its existing API URL; the Brevo key must never be configured in Vercel.

## Last-seen presence and 28-hour reminders

- Presence uses the existing authenticated Server-Sent Events session. The client heartbeats immediately on connect, every 25 seconds while visible, and after returning to a visible/online tab. Server-side heartbeat expiry marks disconnected users offline; `lastSeenAt` writes are throttled to once per minute and are also recorded on disconnect/logout. Presence is only disclosed to accepted connections, direct-conversation peers, and shared-group members, and `hideActivity` is enforced by the server.
- The new `inactivityRemindersEnabled` setting defaults to on for existing and new accounts. Users can turn it off in Settings. An account is considered inactive only when it has a valid stored `lastSeenAt` at least 28 hours old; accounts without a valid timestamp are safely skipped. The app currently has no email-verification workflow/field, so the verified-account badge is not treated as email verification and registered addresses are used as provided.
- The Render blueprint adds a separate `vuprise-inactivity-reminders` Cron Job scheduled every 30 minutes (UTC). It connects to MongoDB, atomically claims each user’s current inactivity period, sends through the existing Brevo API, and records provider acceptance/message ID. Failed sends release the claim for retry; successful sends do not repeat until a later activity begins a new period. An accepted provider response means Brevo accepted the request, not guaranteed inbox delivery.
- Configure `MONGO_URI` and `BREVO_API_KEY` on the Cron Job service in Render, using the same values as the API service. `BREVO_SENDER_EMAIL`, `BREVO_SENDER_NAME` (with `PASSWORD_RESET_FROM` as the fallback), and `CLIENT_URL` are set in the blueprint. The cron service needs outbound HTTPS access to Brevo and MongoDB. Render Cron Jobs incur compute billing with a $1/month minimum service charge; enable the blueprint service only if that recurring cost is acceptable.
- The feature adds nullable user fields and an index; there is no destructive migration. If automatic index creation is disabled, run `User.createIndexes()` once with production database credentials. The reminder is server-side and does not depend on a browser session being open.
- Local test command: `cd server && npm test`. The cron script can be manually invoked with `node scripts/sendInactivityReminders.js` only when pointing at a non-production/test database and using safe provider credentials; tests do not send real email.

## Direct video uploads

- Configure `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, and `CLOUDINARY_API_SECRET` on the Render API service. The API key and cloud name are returned to an authenticated browser as provider identifiers; the API secret is only used on the server to sign a per-upload authorization.
- The browser uploads video bytes directly to Cloudinary. The API receives only a small signing request and a small publish request; video bytes are never posted to Render. The existing image and text post routes remain available.
- The application accepts MP4, WebM, or MOV sources up to 250 MB and validates the stored Cloudinary resource format, byte count, owner/session context, and actual source duration before publishing. The selected trim range must be at most 35 seconds; the published Cloudinary delivery URL applies that range server-side, so client duration values are not trusted for the saved media.
- In Cloudinary Console, keep the account's maximum upload size at or below 250 MB (or the lower limit of your plan) and monitor storage/transformation quotas. Cloudinary account/plan limits are the provider-side protection during transfer; the application also rejects and deletes oversized uploaded resources when finalizing.
- Deploy the MongoDB `VideoUploadSession` collection and the unique sparse `Post.videoUploadSession` index. Mongoose creates declared indexes when automatic index creation is enabled; where it is disabled, run `VideoUploadSession.createIndexes()` and `Post.createIndexes()` once using the API's normal MongoDB credentials.
- Abandoned assets are removed by a periodic cleanup task after 24 hours. Verify that the Render service remains running long enough for the cleanup schedule, or schedule the same exported cleanup function as a Render cron job for stricter cleanup guarantees.
- FFmpeg is no longer needed by the video publish path; it is not required by the API deployment.

## Vuprise AI chat

- The browser only talks to `/api/ai`; the backend proxies every conversation to an OpenCode server over the OpenCode HTTP API. The provider address, credentials, and model identity are never sent to the client, and replies are scrubbed of model/provider names before display.
- The backend reads `OPENCODE_BASE_URL` (default `http://127.0.0.1:4096`), `OPENCODE_MODEL_PROVIDER` (default `opencode`), `OPENCODE_MODEL_ID` (default `deepseek-v4.1-flash-free`), `AI_CHAT_TIMEOUT_MS` (default `90000`), optionally `OPENCODE_WORKSPACE_DIR` (default `/tmp`, see below), and optionally `OPENCODE_SERVER_PASSWORD` / `OPENCODE_SERVER_USERNAME` when the OpenCode server is protected with HTTP basic auth.
- On a managed host such as Render, the loopback default points at the API container itself. With no OpenCode server there, `GET /api/ai/status` reports `available: false` and every chat message answers 503 `AI_UNAVAILABLE` in about a second (connection refused, not a timeout). Set `OPENCODE_BASE_URL` to a reachable OpenCode server and redeploy; startup logs print the effective provider target and warn when the production default is still loopback, and each failed upstream call logs a sanitized `[ai-chat] upstream request failed method=... target=<origin> code=... cause=ECONNREFUSED` line that never contains credentials or payloads.
- The OpenCode free tier only serves requests that originate from an OpenCode process; calling the public inference endpoint directly is rejected (403, `FreeTierError: ... can only be used from within OpenCode`). A real `opencode serve` instance is therefore required - never point `OPENCODE_BASE_URL` at the model gateway itself. Chat requests never carry tool definitions: the free tier rejects any request that includes tools (403), and an all-false tools map is still rejected, so the backend sends plain requests only (the model cannot invoke tools that are not defined).
- The configured model must be one the server actually offers (check `GET {OPENCODE_BASE_URL}/provider`). A wrong `OPENCODE_MODEL_ID` or provider id makes the server answer 500 for every message even though `GET /global/health` still succeeds. A missing session workspace does the same: the `?directory=` value sent to `POST /session` is interpreted by the OpenCode server, so it must already exist on the server's machine - a backend-side temp path (for example the API container's `os.tmpdir()`) does not exist on a separate server container, and every message then answers 500 `UnknownError`. The default workspace is therefore `/tmp`, which exists on the Linux hosts the server runs on; override it with `OPENCODE_WORKSPACE_DIR` when the server runs somewhere `/tmp` is unsuitable (for example Windows). On any upstream 4xx/5xx the backend logs a sanitized `[ai-chat] upstream failure method=... path=... status=... detail="..."` line, and after a 5xx it re-checks the provider's model list once (throttled) and logs which ids the server offers when the configured model is missing - e.g. `configured model "..." is not offered by provider "opencode"`. Neither the provider detail nor the model list is ever sent to the client.
- Running that server: install with `npm install -g opencode-ai` (same version as the requests were verified against, `1.19.2`), then `opencode serve --hostname <host> --port 4096`. On Render, either add it to the API container's build (`npm install -g opencode-ai`) and start it alongside `npm start`, or run it as a private service (internal DNS, for example `OPENCODE_BASE_URL=http://vuprise-ai:4096`). Outside Render, keep it on a private network/VPN or a secured tunnel and set `OPENCODE_SERVER_PASSWORD` - the server has no authentication of its own and anyone who can reach it can execute tools. Free-tier instances also spin down: the first request after an idle period can be dropped (connection closed / 502) while the service restarts, and a model call takes tens of seconds on a small instance, so keep the service warm (a periodic `GET /global/health` with the same basic auth every few minutes) and size the instance for two model calls per message (classifier + chat).
- Verify deployment: `GET /api/ai/status` (authenticated) must return `available: true`, then send one chat message. If it still fails, the boot line, `[ai-chat] upstream request failed` lines (unreachable provider), and `[ai-chat] upstream failure` lines (provider answered an HTTP error, with the offered-model hint when the model id is wrong) identify the misconfiguration without exposing it.
- Image generation stays separate and optional (`AI_IMAGE_API_URL`, `AI_IMAGE_API_KEY`, `AI_IMAGE_MODEL`) and only speaks the OpenAI-compatible Images API.

## Group and upload storage

Group profiles and group messages use the existing MongoDB connection. Group messages are scoped to group membership on every read and write, and are indexed by group and creation time for pagination. The connection model uses a canonical pair-key unique index to prevent duplicate requests in opposing directions. Mongoose builds these declared indexes when automatic index creation is enabled; for managed production databases where `autoIndex` is disabled, deploy and run `Connection.createIndexes()` and `GroupMessage.createIndexes()` once using the API's normal MongoDB credentials. Configure the existing Cloudinary credentials for persistent production media storage; otherwise images are stored in the API's local `uploads` directory and may not survive an ephemeral-host restart.

## Administrator dashboard, moderation, and support

- Configure `ADMIN_EMAILS` on the Render API service as a comma-separated list of exact account email addresses, for example `admin1@example.com,admin2@example.com`. Do not set this as a Vercel `VITE_*` variable. Current local authorized accounts are `vupriseofficial@gmail.com` and `vishnubangaru001@gmail.com`; set them in your local server process to see the admin navigation. Admin access is derived from the authenticated database user's email on every `/api/admin/*` request. A frontend flag or edited local storage cannot grant access.
- Open `/admin` after signing in with an allowlisted account. The Users view uses server-side search, filtering, and pagination. User detail contains stored profile/settings, warnings, and recent posts; administrator APIs do not query or return direct or group message content.
- Temporary/permanent bans, lifts, warnings, and anonymized deletion are persisted in MongoDB. Bans increment `tokenVersion`; protected API requests check moderation status, so an existing session is denied too. Temporary bans expire through an authoritative database check during login/API access, not through a browser countdown. A permanent ban requires an explicit admin lift.
- Warning records remain in the account's moderation history until that user acknowledges them. User deletion first marks the account `deletion_pending` and invalidates sessions, then scrubs login/profile fields, removes authored posts/comments and account-owned message records, removes relationship references, and transfers group ownership where another member exists. If cleanup fails, the account remains inaccessible and an admin can retry deletion. The minimal audit record retains only the user ID and action. Post/message media cleanup is best-effort and its response reports attempted/failed managed assets. Legacy profile avatar/cover URLs without a stored provider ID cannot always be removed from third-party storage; do not interpret account anonymization as proof that an untracked old asset was erased.
- Anonymous requests, ban appeals, deleted-account inquiries, and reports can be submitted at `/support/request`. Requests are limited to five per IP and email per fixed in-process hour; this is a basic per-instance throttle, so use a shared rate-limit store/WAF if the service scales to multiple instances or needs stronger abuse controls. Requests are reviewed under Requests, Reports, or Help; an approved ban appeal requires a separate explicit outcome before it can lift a matching ban. Admin replies are sent through Brevo using the existing `BREVO_API_KEY` and `BREVO_SENDER_EMAIL` (or the `PASSWORD_RESET_FROM` fallback) configuration. The dashboard reports provider acceptance separately from actual inbox delivery; failed email is never claimed as sent. Deleted accounts are not restored by this workflow.
- New MongoDB collections: `supportrequests` and `adminauditlogs`. The `users` collection receives moderation status, expiration, reason, and warning-history fields. Mongoose applies declared indexes when automatic index creation is enabled. If production disables `autoIndex`, run `SupportRequest.createIndexes()`, `AdminAuditLog.createIndexes()`, and `User.createIndexes()` once through a controlled backend migration/deployment command.
- Public endpoints: `POST /api/support/requests`. Admin endpoints require an authenticated allowlisted user: `GET /api/admin/overview`, `/users`, `/users/:id`, `/users/:id/posts`, `/requests`, `/reports`, `/help`; moderation writes use `/users/:id/{temporary-ban,permanent-ban,lift-ban,warnings,delete}`; inbox changes use `PATCH /api/admin/inbox/:id`. Warning acknowledgment requires the affected user's own session at `POST /api/auth/warnings/:warningId/acknowledge`.
- Run API tests with `cd server && npm test`; run frontend checks with `cd client && npm test`, `npm run lint`, and `npm run build`. Deploy the backend to Render first with `ADMIN_EMAILS`, then deploy the frontend to Vercel. The new user fields are additive and need no destructive migration; schedule the indexes above if `autoIndex` is disabled.

## SEO, privacy notice, and abuse protection

- The client build now emits `robots.txt`, `sitemap.xml`, one static HTML file per fixed route (`faq.html`, `privacy.html`, `support/request.html`, auth/app pages), and `404.html`. `client/vercel.json` uses `cleanUrls: true` plus scoped rewrites for the dynamic `/post/:id`, `/profile/:id`, and `/groups/*` deep links, so unknown paths answer with a real 404 status and public pages answer with a real 200. Keep the rewrite list in sync when new dynamic routes are added; the client `seo.test.mjs` and `scripts/vite-seo-plugin.mjs` enforce and generate the artifacts.
- Optional client variables: `VITE_SITE_URL` sets the canonical origin used in the sitemap, robots.txt, canonical tags, and Open Graph URLs (falls back to `https://nexora-lac-three.vercel.app`). `VITE_GA4_MEASUREMENT_ID` enables GA4, which loads only after a visitor accepts analytics in the privacy notice; consent is stored under the `vuprise_consent_v1` localStorage key and can be re-opened from the footer Cookie settings. Regenerate the social share card after branding changes with `cd client && node scripts/generate-og-image.mjs`.
- Abuse protection: API rate limits moved from in-process memory to the new `ratelimitcounters` collection (keys are HMAC digests; documents expire automatically). Support intake is limited to 5 per hour per connection and per email, identical submissions inside 10 minutes are treated as already received, registration is limited to 20 per hour per connection, and failed sign-ins are limited to 10 per 15 minutes per connection and email. Hidden `website` honeypot fields are checked on register, login, password reset, and support submits. If production disables `autoIndex`, run `RateLimitCounter.createIndexes()` once.
- The API adds baseline security headers (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, HSTS in production), rejects disallowed CORS origins with 403, and returns a generic message for production 5xx errors. JSON bodies are limited to 1mb; evidence photos and broadcast images use multipart routes with their existing 5 MB limits. Inactivity-reminder cron and admin moderation flows are unchanged.
